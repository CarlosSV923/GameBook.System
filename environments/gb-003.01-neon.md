# GB-003.01 — Entornos Neon por ambiente

Este registro define la separación de base de datos para producción y
pruebas. No contiene nombres de proyecto, IDs, URLs de conexión, contraseñas,
tokens ni valores de variables. Las conexiones se referencian únicamente por
nombre de variable, como exige `tasks/mvp.md`.

## 1. Evidencia recibida y alcance

- El autor confirmó el 2026-09-23 que ya creó el proyecto Neon y dos ramas:
  describió la rama de producción como `main` y la de pruebas como `develop`.
  La consulta posterior con Neon CLI aclaró que el **nombre real** de la rama
  primaria es `production`, no `main`; `main` es la rama Git de despliegue.
- La dependencia `GB-002` figura `[ RESOLVED ]` en
  [`../tasks/mvp.md`](../tasks/mvp.md).
- El autor también confirmó una cuenta Vercel y autenticación de su CLI. La
  vinculación de proyectos Vercel, dominios y previews pertenece a `GB-003.03`
  y no se ejecuta aquí.
- La CLI `vercel` no está disponible en el PATH aislado de Codex; no se
  instalaron herramientas ni se solicitaron credenciales adicionales. La
  confirmación del autor es la evidencia de Vercel fuera del alcance de esta
  subtarea.

## 2. Mapa de ambientes

| Ambiente lógico | Rama Neon confirmada | Uso | Datos permitidos |
| --- | --- | --- | --- |
| `production` | `production` | Base para despliegues finales desde Git `main` en `GB-012`. | Datos de producción; no usar en pruebas destructivas. |
| `test` / `preview` | `develop` | Integración, migraciones de prueba y previews antes de producción. | Datos ficticios o aislados; nunca credenciales ni datos de producción. |

La rama de Neon y la rama Git no son la misma entidad. Este registro solo fija
el mapa de ambientes de Neon; `GB-003.03` decidirá la vinculación de Vercel y
los orígenes de preview. No se copian ni se inventan dominios.

## 3. Conexiones por servicio

Cada microservicio tendrá una conexión runtime y otra directa para migraciones.
Los valores se cargarán en el entorno del proyecto y no se escriben aquí.

| Servicio | Runtime serverless | Migración directa | Esquema runtime permitido |
| --- | --- | --- | --- |
| AuthUser | `AUTH_DATABASE_URL` | `AUTH_DATABASE_DIRECT_URL` | `auth` únicamente |
| Game | `GAME_DATABASE_URL` | `GAME_DATABASE_DIRECT_URL` | `game` únicamente |

Reglas:

1. El runtime AuthUser no consulta ni escribe el esquema `game`.
2. El runtime Game no consulta ni escribe el esquema `auth`.
3. El UUID del `sub` se guarda en Game como referencia lógica, sin FK entre
   esquemas.
4. Las migraciones usan la variable `*_DATABASE_DIRECT_URL` solo en GitHub
   Actions del backend correspondiente, antes del despliegue que necesita el
   cambio. Los migradores heredados de Neon tienen privilegios amplios; la
   limitación a un esquema es operativa, según `GB-003.02`.
5. Las funciones runtime usan la variable `*_DATABASE_URL` compatible con el
   patrón serverless que se confirme en `GB-003.02`.
6. Ningún build o arranque de Vercel ejecuta migraciones implícitas contra
   `main`/producción.
