# GB-003.02 — Aislamiento de esquemas y migraciones

Este registro documenta el cierre de los límites runtime PostgreSQL en Neon.
No contiene contraseñas, tokens, URLs de conexión ni valores de variables.
La subtarea queda `[ RESOLVED ]` con aislamiento runtime comprobado y un
límite operativo, no de permisos SQL, para las migraciones.

## 1. Alcance y recursos comprobados

- Dependencias `GB-003.01` y `GB-002` figuran `[ RESOLVED ]` en
  [`../tasks/mvp.md`](../tasks/mvp.md).
- Proyecto consultado en Neon: `GameBook-db` (`little-shape-45554749`). El
  identificador no es un secreto, pero no se usan URLs ni credenciales en este
  registro.
- La API de Neon informa las ramas `production` (primaria) y `develop`.
  `production` corresponde a Git `main` en el despliegue final; no existe una
  rama Neon llamada `main`. La evidencia previa de `GB-003.01` usó ese nombre
  como denominación lógica y se corrigió en su registro.
- No se ejecutaron migraciones ni se crearon tablas.

## 2. Esquemas y roles preparados

En las ramas `production` y `develop` se prepararon los mismos nombres:

| Servicio | Esquema | Migrador heredado (no usar en CI) | Runtime limitado |
| --- | --- | --- | --- |
| AuthUser | `auth` | `gamebook_auth_migrator` | `gamebook_auth_app` |
| Game | `game` | `gamebook_game_migrator` | `gamebook_game_app` |

Los esquemas pertenecen a sus respectivos migradores. Los roles SQL `*_app`
se crearon con `LOGIN` y `NOINHERIT`, sin membresía en `neon_superuser`.
Cada uno recibió `USAGE` únicamente sobre su propio esquema, sin `CREATE`
en base o esquemas. Los migradores concedieron privilegios por defecto de
tablas y secuencias futuras exclusivamente al runtime correspondiente.
No existen todavía tablas de aplicación.

El mapeo de conexión previsto queda separado por rol, sin escribir sus
valores:

| Variable | Rol | Método | Esquema |
| --- | --- | --- | --- |
| `AUTH_DATABASE_URL` | `gamebook_auth_app` | Vercel runtime/serverless | `auth` |
| `AUTH_DATABASE_DIRECT_URL` | Nuevo migrador SQL por definir en `GB-003.06` | GitHub Actions AuthUser, después de prueba | `auth` por permisos |
| `GAME_DATABASE_URL` | `gamebook_game_app` | Vercel runtime/serverless | `game` |
| `GAME_DATABASE_DIRECT_URL` | Nuevo migrador SQL por definir en `GB-003.06` | GitHub Actions Game, después de prueba | `game` por permisos |

## 3. Evidencia de verificación

- En `develop` y `production`, `auth` pertenece a `gamebook_auth_migrator` y
  `game` a `gamebook_game_migrator`. No hay tablas de aplicación.
- Con conexiones **reales** como cada `*_app`, Neon CLI devolvió en las dos
  ramas: `neon_superuser=false`, `USAGE=true` para el esquema propio,
  `USAGE=false` para el ajeno y `CREATE=false` en ambos esquemas y la base.
- Las ACL por defecto de tablas/secuencias en `auth` solo conceden acceso a
  `gamebook_auth_app`; las de `game` solo a `gamebook_game_app`.
- Los antiguos `gamebook_auth_runtime` y `gamebook_game_runtime`, creados
  mediante la API y miembros heredados de `neon_superuser`, se retiraron de
  las dos ramas después de comprobar que no poseían relaciones, esquemas ni
  ACL por defecto. Su eliminación retiró sus grants antiguos. Los roles
  `*_app` continuaron conectando y los grants por defecto siguieron vigentes.
- Los dos migradores sí heredan `neon_superuser`. La prueba inicial de
  `REVOKE neon_superuser`/`ALTER ROLE NOINHERIT` fue denegada por Neon; no se
  afirma aislamiento SQL para esas credenciales.
