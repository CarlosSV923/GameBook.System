# GameBook — Plan de ejecución del MVP

## 1. Alcance, autoridad y estado

Este documento organiza **cómo implementar** el MVP descrito en [`../specs/mvp.md`](../specs/mvp.md). Las subtareas ejecutables, sus estados y dependencias se registran en [`../tasks/mvp.md`](../tasks/mvp.md). Los tres repositorios de aplicación ya existen; este plan no autoriza por sí solo a ejecutar tareas pendientes, desplegar o publicar datos. El contrato de implementación vigente es [`GB-002-CONTRACTS-v3`](../contracts/contract-baseline-v3.md), con IGDB; v1/v2 y RAWG se conservan solo como historial. El estado de cada tarea es exclusivamente el de `tasks/mvp.md`.

La especificación manda sobre el plan. Si una decisión técnica exige cambiar una conducta del producto, se detiene la tarea, se pregunta al autor **una cuestión a la vez**, se actualiza primero `specs/mvp.md` y luego este plan. Cada tarea implementada deberá enlazar el criterio funcional correspondiente; ninguna herramienta de IA debe añadir funcionalidades por inferencia.

### Resultado esperado

Tres repositorios **públicos** e independientes para las aplicaciones, integradas y aceptadas primero en local y desplegadas **solo desde `main`** al final: AuthUser y Game en Render, y Frontend en Vercel si corresponde. No habrá Vercel Preview para los backends. Neon e IGDB/Twitch conservarán credenciales separadas para pruebas locales y producción. Una visita puede consultar IGDB sin sesión; una persona autenticada administra solo sus favoritos. Los dos microservicios exponen Swagger UI público para evaluación del portfolio. **Después** de terminar las implementaciones se creará un cuarto repositorio público, `GameBook.System`, solo para documentación integral y bilingüe del sistema final. La [enmienda operativa local-first](../environments/deployment-policy-local-first.md) prevalece sobre cualquier referencia histórica a previews en contratos congelados.

## 2. Decisiones de arquitectura que rigen el trabajo

| Límite | Estrategia de implementación |
| --- | --- |
| `GameBook.Microservice.AuthUser` | NestJS con capas de dominio, aplicación (casos de uso), infraestructura (Prisma, JWT, hashing) y presentación (HTTP/Swagger). Posee cuentas y emisión/revocación de JWT. |
| `GameBook.Microservice.Game` | NestJS con las mismas capas. Posee favoritos y verifica el JWT recibido del navegador; no consulta tablas de AuthUser. |
| `GameBook.Frontend` | Next.js con módulos por función (catálogo, autenticación, favoritos, perfil, preferencias), componentes compartidos pequeños y adaptadores de API. Su código de servidor consulta IGDB; su navegador llama a AuthUser y Game. |
| `GameBook.System` | Repositorio documental, sin aplicación ni despliegue Vercel. Se crea al final para reunir documentación general, artefactos SDD bilingües y arquitectura final verificada. |
| PostgreSQL | **Una** base Neon con esquemas `auth` y `game`. Cada Prisma Client y cada historial de migraciones pertenecen a su esquema. Runtime con roles SQL limitados; `GB-003.06` debe probar migradores SQL limitados antes de entregarlos a Actions. Los migradores antiguos con privilegio amplio no se usarán en CI. No crear claves foráneas entre ambos esquemas: Game guarda el UUID autenticado como referencia lógica. |
| IGDB | Solo el servidor Next.js usa `IGDB_CLIENT_ID` y `IGDB_CLIENT_SECRET`, obtiene/renueva un token OAuth de aplicación desde Twitch y consulta IGDB v4; sus rutas validan parámetros y nunca reenvían secreto ni token. |
| Contratos | HTTP JSON versionado bajo `/v1` para ambos microservicios, documentado con OpenAPI. No se comparte código de dominio ni Prisma Client entre repositorios. |

### 2.1 Organización de proyectos y gestor de paquetes

Se adopta la estructura propuesta por el autor para **ambos** microservicios. `api/` es la capa de presentación HTTP (el equivalente de `presentation/` en la propuesta anterior); se mantiene ese nombre para que el árbol resulte evidente a un reclutador. Dentro de cada capa podrán crearse subcarpetas por contexto (`auth`, `users`, `favorites`) cuando ayuden a mantener los archivos pequeños, sin mezclar dependencias en dirección contraria.

```text
GameBook.Microservice.AuthUser/ o GameBook.Microservice.Game/
├─ src/
│  ├─ api/             # controladores, DTO HTTP, validación, guards, Swagger
│  ├─ application/     # casos de uso, servicios de aplicación y puertos
│  ├─ domain/          # entidades, value objects, reglas y contratos de repositorio
│  ├─ infrastructure/  # Prisma, repositorios concretos, JWT/criptografía, logging
│  └─ main.ts          # arranque y composición de NestJS
├─ tests/
│  ├─ unit/            # reglas y casos de uso aislados
│  └─ integration/     # API, Prisma y límites entre servicios
├─ prisma/             # schema.prisma y migraciones propias del servicio
├─ package.json
└─ pnpm-lock.yaml
```

`src/api → src/application → src/domain` es la dirección principal de dependencias; `infrastructure` implementa los contratos definidos hacia dentro. El dominio no importará NestJS, Prisma ni HTTP. Las pruebas no se dispersarán entre archivos de producción: residirán en `tests/unit` y `tests/integration`. Si una herramienta propone otra organización, deberá justificar por qué mejora legibilidad **sin perder** estos límites y obtener revisión antes de cambiar el plan. El frontend mantendrá su estructura idiomática de Next.js, con módulos `features/` y `shared/`, componentes pequeños y adaptadores tipados.

Los **tres repositorios** usarán `pnpm`, cada uno con su propio `package.json`, versión de gestor fijada y `pnpm-lock.yaml` versionado. Los scripts de desarrollo, formato, lint, tipos, pruebas y build se invocarán con `pnpm`; CI instalará dependencias con lockfile inmutable. No se mezclarán lockfiles de npm/yarn ni se introducirá un workspace que una los tres repositorios. Se revisará el tamaño de archivos durante cada PR y se extraerán responsabilidades cuando una clase o componente mezcle reglas, infraestructura y presentación.

### 2.2 Identidad y revocación

AuthUser firmará con una clave privada; Game verificará localmente con la pública. Se fija **RS256** como algoritmo de contrato del MVP, con verificación estricta de algoritmo, emisor, audiencia, `sub` UUID, `iat` y `exp` (una hora). El JWT incluirá una versión de sesión (`ver`); AuthUser persistirá la versión actual por usuario. Al cambiar la contraseña, incrementará esa versión en la misma operación persistente que actualiza el hash: todo JWT anterior quedará revocado, incluido el actual. El frontend limpiará `sessionStorage` y llevará a inicio de sesión.

En **cada** operación protegida, Game primero verifica localmente firma y expiración y después consulta un endpoint de validación de sesión de AuthUser con el mismo Bearer JWT. AuthUser compara `ver` con el valor vigente. Un token revocado recibe `401`; si AuthUser no responde, Game **falla cerrado** y devuelve un error temporal sin leer ni modificar favoritos. La disponibilidad de AuthUser se convierte por ello en dependencia operacional explícita de Game. AuthUser aplica la misma comprobación de versión a sus propios endpoints protegidos. La expiración o una respuesta `401` limpia la sesión del frontend; ninguna solicitud pública necesita JWT. No se introduce refresh token.

Las contraseñas se almacenarán solo como hash con sal mediante un algoritmo de derivación apto para contraseñas; jamás en texto plano, logs o respuestas. El registro exige las reglas de `specs/mvp.md`, correo único y confirmación coincidente. El registro exitoso **no** inicia sesión: navega a inicio de sesión. El frontend puede usar `exp` para anticipar el cierre visual, pero la decisión de autorización siempre corresponde a los servicios.

### 2.3 Persistencia mínima y sincronización

AuthUser es dueño de `User`: UUID, nombre completo, correo normalizado único, hash de contraseña y versión de sesión. Game es dueño de `Favorite`, con clave lógica única `(userId, igdbId)` y únicamente nombre, fecha de lanzamiento opcional, URL de imagen opcional, puntuación opcional y plataformas. Para plataformas se propone una relación hija con ID de plataforma IGDB y nombre mostrado; permite filtrar por ID y construir tarjetas sin duplicar datos adicionales del juego. El filtro anual deriva de la fecha; si falta fecha, ese favorito no coincide con un filtro de año. Se usarán tipos de fecha sin zona horaria para el lanzamiento y valores nulos cuando IGDB no aporte un campo.

La tarjeta de favoritos procede de esta instantánea local. Abrir el modal siempre solicita detalle a IGDB por medio de Next.js. Si llega correctamente, Next.js entrega el detalle al navegador y se envía a Game una actualización de **solo** los campos básicos de la instantánea; el listado visible se actualiza tras confirmación. Si IGDB falla, no se envía actualización: permanecen la tarjeta y el favorito, y el modal explica que el detalle no está disponible. La API de Game valida tipo, longitud y pertenencia de la instantánea al usuario, pero los datos de catálogo proceden del flujo IGDB del frontend; no hará una segunda llamada duplicada a IGDB por cada detalle. No habrá sincronización masiva ni periódica.

## 3. Contratos que se deben cerrar antes del trabajo paralelo

La tarea `GB-002` producirá y revisará las especificaciones OpenAPI, ejemplos y pruebas de contrato **antes** de que los tres proyectos implementen consumidores y servidores en paralelo. Las rutas de esta tabla son la base técnica propuesta para ese contrato; si durante `GB-002` cambia un nombre, se actualizan aquí y en los tres repositorios antes de escribir adaptadores dependientes.

| Servicio | Operación prevista | Entrada y efecto verificable |
| --- | --- | --- |
| AuthUser | `POST /v1/auth/register` | Nombre completo, correo, contraseña y confirmación. Crea usuario único; devuelve identidad pública, nunca hash ni JWT. |
| AuthUser | `POST /v1/auth/login` | Correo y contraseña; devuelve `accessToken`, `tokenType`, `expiresIn=3600` e identidad mínima. Credenciales erróneas: mensaje genérico. |
| AuthUser | `GET /v1/auth/session` | Bearer JWT; verifica firma, caducidad y versión vigente; devuelve identidad mínima. Game lo consulta para revocación. |
| AuthUser | `PATCH /v1/users/me/password` | Bearer JWT, contraseña actual y nueva; cambia hash, incrementa versión y revoca todas las sesiones anteriores. |
| Game | `GET /v1/favorites` | Bearer JWT; filtros opcionales `name`, `platformId`, `yearFrom`, `yearTo`, `page` y `pageSize`; devuelve resultados del usuario y metadatos para desplazamiento infinito. |
| Game | `GET /v1/favorites/suggestions` | Bearer JWT, tipo `name` o `platform` y texto parcial; devuelve sugerencias acotadas de **todos** los favoritos propios, no solo de la página cargada. |
| Game | `POST /v1/favorites` | Bearer JWT y datos básicos de IGDB; crea una entrada de ese usuario o devuelve un conflicto identificable si ya existe. |
| Game | `PATCH /v1/favorites/{igdbId}/snapshot` | Bearer JWT y datos básicos actualizados después de un detalle IGDB exitoso; solo modifica el favorito propio existente. |
| Game | `DELETE /v1/favorites/{igdbId}` | Bearer JWT; elimina únicamente el favorito propio después de la confirmación hecha por la UI. |
| Next.js | Rutas servidoras de catálogo, detalle y plataformas | Parámetros seguros de búsqueda, filtros y página; obtienen/renuevan token de aplicación de Twitch y consultan IGDB v4. Estas rutas no requieren JWT de GameBook. |

`GB-002` fijará por campo obligatoriedad, nulabilidad, normalización, códigos HTTP, estructura uniforme de error, límites de paginación, ejemplos **ficticios**, esquema Bearer de Swagger y versión de cada contrato. Como base: `400` validación, `401` autenticación inválida/revocada, `404` recurso propio inexistente, `409` correo/favorito duplicado, `503` dependencia AuthUser indisponible para Game. No se devuelve información de otro usuario para distinguir si su favorito existe. El cuerpo de error tendrá un código estable para que el frontend traduzca mensajes a inglés/español sin depender del texto del servidor. Los filtros `name`, `platformId` y año se combinan con **AND**; el año único se normaliza a `yearFrom=yearTo`, y los intervalos son inclusivos. La lista se ordena de forma determinista para paginar; tras guardar, eliminar, cambiar filtros o sincronizar una instantánea, el frontend reinicia la paginación y evita tarjetas duplicadas por `igdbId`.

El mapeo IGDB → tarjeta/detalle está en [`../contracts/igdb-mapping.md`](../contracts/igdb-mapping.md): `igdbId`, `first_release_date`, `cover.image_id`, `platforms`, `summary`, géneros, desarrolladores y `total_rating` de 0–100. Las sugerencias públicas provienen de IGDB y las de favoritos de Game, sin limitarse a favoritos ya cargados en pantalla; serán consultas acotadas con espera breve entre pulsaciones y cancelación de peticiones obsoletas. Seleccionar una sugerencia aplica el texto o ID correspondiente. El catálogo inicial sin nombre se ordena por `total_rating` descendente; la búsqueda por nombre puede seguir la relevancia de IGDB. El proxy usa `limit`/`offset` y nunca acepta URL o APICalypse arbitrario del navegador; no se asumirá traducción de contenido.

### Entregables de contrato

- OpenAPI de cada servicio, versionado en su repositorio; Swagger UI consultable en producción de `main` y protegido solo para probar operaciones Bearer, no para leer la documentación.
- Ejemplos de solicitudes/respuestas anonimizados y fixtures de éxito, validación, duplicado, expiración, revocación y dependencia caída.
- Matriz de variables de entorno con propietario y alcance (sin valores), nombres estables de endpoints y URLs base para desarrollo local y producción. No se define ambiente Vercel Preview.
- Adaptadores tipados del frontend implementados **contra esos contratos**, con dobles de prueba; cualquier cambio incompatible se versiona, se anuncia a los otros dos repositorios y se prueba antes de fusionar.

Varias herramientas de IA pueden ejecutar **subtareas diferentes en repositorios distintos** al mismo tiempo; si se divide un repositorio, se delimitan archivos y contratos para que dos herramientas no editen lo mismo.

## 5. Protocolo SDD para varias herramientas de IA

1. La coordinación mantiene `specs/mvp.md` y este plan como referencia común. Antes de asignar una tarea, crea o actualiza el issue de GitHub con ID `GB-###`, repo dueño, secciones de especificación, contrato aplicable, dependencias, entregables y criterios de aceptación.

3. Antes de implementar, la herramienta escribe o revisa las pruebas/ejemplos del contrato afectado y confirma que no altera rutas, payloads ni significado de errores congelados. Los cambios de contrato requieren aprobación de coordinación y actualización sincronizada de consumidores/productores.
4. Cada tarea de **aplicación** trabaja desde `develop` en su rama `feature/[task-number]/[resumen-de-tarea]`. La publicación inicial del repositorio y la creación/consulta de PR se gestionan con `gh`; los commits y push de cambios usan Git. El PR hacia `develop` incluye resumen en inglés, enlaces a requisito/issue/contrato, archivos o módulos modificados, pruebas ejecutadas, resultados, limitaciones y capturas cuando cambie la UI. Cada PR creado se registra inmediatamente en `tasks/mvp.md` bajo su subtarea, con repositorio, URL, ramas y estado; también se registran los PR `develop → main` y los de release-please. `GB-014` es la excepción: prepara localmente `GameBook.System` completo y hace una sola publicación inicial a `main`, sin rama `develop` ni PR propio.
5. La herramienta entrega una nota de traspaso: qué hizo, qué no hizo, decisiones técnicas, comandos de verificación, resultado de CI, migraciones/variables necesarias y cualquier riesgo para las otras tareas. Cuando el autor notifique que los completó, la coordinación verifica en GitHub el estado `MERGED`, la rama de destino y los criterios de aceptación de **todos** los PR de la subtarea; entonces actualiza el registro y, si procede, la marca `[ RESOLVED ]`. Un PR abierto o cerrado sin merge mantiene la subtarea sin resolver.
6. En las aplicaciones, las verificaciones de tareas y documentación durante el desarrollo se realizan sobre `develop` (o sobre su PR hacia `develop`); la ausencia de esos cambios en `main` no bloquea ni reabre tareas. **Solo después de completar todas las implementaciones y superar las puertas previas a producción de §9**, el autor integra `develop` en `main` en `GB-012`. Después de cada release PR de release-please fusionado en `main`, se sincroniza `main` de vuelta a `develop` para conservar manifiestos/versiones y evitar divergencias. Cada PR de publicación y release sigue el mismo registro y verificación posterior. Este flujo no aplica al repositorio documental de publicación única.

Las pruebas automatizadas usarán valores ficticios y claves de prueba; las pruebas locales reales obtendrán secretos de desarrollo mediante archivos/variables privados ignorados por Git, nunca de producción. Los secretos de producción se cargarán en Render/Vercel/GitHub solo en la etapa final y según el proveedor dueño. Un contrato publicado nunca se sustituye silenciosamente: el cambio RAWG→IGDB tiene revisión explícita [`GB-002-CONTRACTS-v3`](../contracts/contract-baseline-v3.md), que sustituye v1/v2 para la implementación del proveedor sin borrar su evidencia histórica.

## 6. Estrategias de implementación por componente

### 6.1 AuthUser

- Casos de uso separados: registrar usuario, iniciar sesión, consultar sesión vigente y cambiar contraseña. Repositorio abstracto de usuarios, servicio de hashing y firmador/verificador como puertos; adaptadores en infraestructura.
- Normalizar correo antes de aplicar unicidad, sin revelar si una contraseña concreta fue incorrecta durante login. Validar en frontera HTTP y reforzar invariantes en el dominio. Manejar la carrera de registros duplicados mediante índice único y traducción a `409`.
- Incluir `sub` UUID y versión en el JWT. Firmar con la clave privada de entorno; verificar dentro de AuthUser; configurar emisor/audiencia compartidos por contrato. El cambio de contraseña compara el hash actual, actualiza el nuevo y aumenta versión de sesión atómicamente.
- Swagger cubre seguridad Bearer, restricciones de campos y errores. Los logs en inglés registran evento, resultado, `requestId` y `userId` cuando se conozca, pero no cuerpos con contraseñas ni JWT.

### 6.2 Game

- Casos de uso separados: guardar, listar con filtros, sugerir nombres/plataformas, actualizar instantánea y eliminar favorito. Los repositorios reciben el `userId` extraído del JWT validado; ningún endpoint acepta `userId` como autoridad del navegador.
- Índice único `(userId, igdbId)` para impedir duplicados incluso con solicitudes simultáneas. Filtros por nombre sin distinguir mayúsculas/minúsculas, plataforma IGDB y años inclusivos; ordenar de manera estable y usar paginación acotada para el desplazamiento infinito.
- Guardias HTTP: validar JWT asimétrico localmente, consultar sesión vigente en AuthUser, autorizar solo el usuario `sub`. Distinguir `401` por token inválido/revocado de `503` por indisponibilidad de AuthUser. Cada ruta y Swagger declaran Bearer.
- La actualización de instantánea solo afecta campos básicos de un favorito existente del usuario; no crea favoritos implícitamente. El fracaso de IGDB se maneja en frontend sin llamar a esta operación.

### 6.3 Frontend

- Un cliente para AuthUser, otro para Game y un adaptador servidor para IGDB. El token vive en `sessionStorage`, no en `localStorage` ni en una variable `NEXT_PUBLIC_`; se adjunta solo a peticiones protegidas. Ante `401` de AuthUser/Game se borra, se actualiza el estado de navegación y se exige nuevo login; `503` no se confunde con credenciales inválidas.
- Tema: preferencia inicial `prefers-color-scheme`; elección manual persistida localmente para visitantes y usuarios, aplicada temprano para evitar destellos de tema. Idioma: inglés inicial independiente del navegador; elección EN/ES persistida localmente. Ambas preferencias se conservan al cambiar vistas, filtros o sesión. IGDB conserva sus textos originales.
- Componentes reutilizables para tarjeta, filtros, modal y estados en catálogo/favoritos. Mantener acciones de guardar/eliminar contextuales e independientes del clic que abre la tarjeta. Confirmaciones accesibles; el modal permite foco controlado, teclado y cierre. Mensajes de carga/éxito/error y todos los textos propios proceden del catálogo de traducciones.
- El servidor Next.js obtiene y renueva el token OAuth de aplicación de Twitch; encapsula IGDB v4 con `POST` y consultas APICalypse construidas solo desde parámetros permitidos. Usa `limit`/`offset`, caché prudente para respuestas públicas y debounce/cancelación de sugerencias. Respeta 4 solicitudes/s y 8 concurrentes como límites documentados, contempla `429` aun con múltiples instancias Vercel y reintentos acotados. Muestra atribución enlazada a IGDB donde usa sus datos/imágenes. Trata descripciones externas como contenido no confiable y evita HTML ejecutable. Si faltan imagen o campos, ofrece sustitutos visuales o ausencia explícita sin inventar hechos.
- En favoritos, filtrar y cargar desde Game sin recuperar cada detalle IGDB para pintar tarjetas. Solo el modal pide detalle a IGDB; el éxito dispara la sincronización básica y un fallo conserva instantánea/acción de eliminar. Cerrar sesión limpia token y estado privado y navega a la consulta pública.

### 6.4 Integración de los tres repositorios en local

`GB-012.10` conserva la evidencia histórica de la primera orquestación Docker Compose en `GameBook.Frontend`, con los tres repositorios clonados como hermanos y documentados en ambos README. `GB-014.12` trasladará la orquestación documental a `GameBook.System`: sus contextos seguirán siendo esos clones hermanos, podrá añadir Dockerfiles de **desarrollo** en los repositorios dueños mediante PR separados y levantará una imagen local de PostgreSQL como dependencia por defecto. Neon no será obligatorio; solo se usará mediante una configuración explícita alternativa. Las migraciones de los esquemas seguirán siendo una operación controlada y Compose no recibirá secretos de migración ni las ejecutará al arrancar. Los valores locales JWT y Twitch/IGDB se cargarán desde configuración privada ignorada por Git; las plantillas solo enumerarán nombres. La prueba de arranque no sustituye la aceptación funcional completa de `GB-012.01`.

## 7. Pruebas, observabilidad y seguridad

| Nivel | Cobertura mínima antes de integración |
| --- | --- |
| Unitarias AuthUser | Reglas de registro/contraseña, duplicado, credenciales erróneas, firma/claims, expiración y aumento de versión al cambiar contraseña. |
| Integración AuthUser | HTTP + Prisma en base aislada de prueba: unicidad real, login, sesión válida/revocada, cambio de contraseña y contrato OpenAPI. |
| Unitarias Game | Aislamiento por UUID, filtros combinados, duplicado, sincronización y eliminación. |
| Integración Game | HTTP + Prisma en esquema/base de prueba, JWT firmado por clave de prueba AuthUser; token válido, ausente, manipulado, vencido, revocado, usuario ajeno y AuthUser caído. |
| Unitarias/integración Frontend | Preferencias, traducciones, filtros, sugerencias, paginación, confirmaciones, formularios, token/expiración, estados IGDB y sincronización. Usar respuestas simuladas; ninguna prueba unitaria consume cuota IGDB. |
| Humo entre aplicaciones | Registro→login→guardar→ver/filtrar→abrir/sincronizar→eliminar→cambiar contraseña→verificar revocación→nuevo login→logout; visita pública sin JWT y Swagger UI de ambos servicios. |

En ambos backends, las pruebas unitarias vivirán en `tests/unit/` y las de integración en `tests/integration/`, con configuración y comandos de `pnpm` separados para ejecutarlas individualmente o juntas. Las pruebas de persistencia usarán una base o rama Neon **de prueba**, nunca producción, con esquemas independientes y limpieza controlada. CI ejecutará con `pnpm` al menos formato/lint, tipos, unitarias, integración pertinente, validación OpenAPI y build; instalará según el `pnpm-lock.yaml` del repositorio sin modificarlo. Los logs de ambos backends serán estructurados y legibles en inglés, con `requestId`, operación, resultado, duración, código HTTP y UUID cuando se haya autenticado; no incluirán secretos ni datos sensibles. El frontend propagará un identificador de petición cuando sea útil para correlación, sin poner JWT en logs.

La revisión de seguridad verificará validación y límites de entrada, CORS limitado a los orígenes del frontend local y luego productivo, control de acceso por `sub`, errores sin detalles internos, Client Secret y token de aplicación IGDB solo servidor, aislamiento de archivos locales y variables Vercel, respuestas privadas sin caché compartida y revocación efectiva. Se probarán fallos de Twitch/IGDB y de AuthUser sin pérdida de datos. La revisión de accesibilidad cubrirá teclado, foco, contraste en ambos temas, etiquetas de formularios y avisos de estado; el desplazamiento infinito tendrá indicación de carga y fin de resultados.

La ejecución de CI y la revisión del diff siguen siendo evidencia de calidad para cerrar tareas, pero no barreras técnicas de merge. El cuerpo del PR explicará el objetivo y las pruebas en inglés. [Referencia oficial de release-please](https://github.com/googleapis/release-please-action).

Neon aloja una base con los dos esquemas. Las conexiones de ejecución usan roles SQL `*_app` que solo tienen acceso a su propio esquema. Los actuales `*_migrator` heredan `neon_superuser` y no se entregarán a GitHub Actions. En `GB-003.06`, crear nuevos migradores SQL sin esa membresía y conceder `USAGE`/`CREATE` solo en su esquema, sin `CREATE` sobre la base; como no hay tablas de aplicación todavía, los objetos de las primeras migraciones podrán pertenecer al nuevo migrador. El proceso de CI/CD aplicará migraciones ya versionadas: en Prisma v7 `migrate deploy` no necesita shadow database, mientras `migrate dev` sí la necesita y queda fuera de los Actions de despliegue. Fijar versión y comando exacto al implementar. Si la limitación de Neon o una migración Prisma concreta exige más permisos, no ampliar el rol silenciosamente: documentar el fallo y pedir decisión. [Prisma: shadow database](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/shadow-database), [Prisma: despliegue en GitHub Actions](https://docs.prisma.io/docs/orm/prisma-client/deployment/deploy-database-changes-with-prisma-migrate).

En `develop` podrán activarse tras integrar cambios de migración. En producción, la ejecución controlada desde `main` deberá terminar **antes** de crear/configurar el servicio Render que despliegue el código dependiente; el merge simultáneo no garantiza ese orden. `GB-012` establecerá y probará esta puerta de despliegue. GitHub requiere que un workflow manual exista en la rama predeterminada, de modo que no se presupone ejecución manual desde `develop` mientras `main` aún no lo contiene. [GitHub workflow_dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Variables previstas, con nombres definitivos en [`../contracts/persistence-igdb.md`](../contracts/persistence-igdb.md) y calendario **vigente** en [`../environments/deployment-policy-local-first.md`](../environments/deployment-policy-local-first.md): AuthUser (URL runtime de su esquema, clave privada JWT, emisor/audiencia y orígenes permitidos); Game (URL runtime de su esquema, clave pública JWT, URL AuthUser, emisor/audiencia y orígenes); Frontend (URL pública AuthUser, URL pública Game, `IGDB_CLIENT_ID` y `IGDB_CLIENT_SECRET` privados). ## 10. Riesgos y límites explícitos

- **Dependencia de AuthUser para revocación inmediata:** Game no permite operaciones protegidas cuando AuthUser no puede confirmar vigencia. Se mide y prueba esa indisponibilidad; no se degrada a aceptar tokens potencialmente revocados.
- **Límites y disponibilidad IGDB/Twitch:** renovar el token de aplicación por `expires_in`, aplicar consultas acotadas, cancelación de sugerencias, caché pública prudente y estados de error; cubrir `401`/`403`/`429`/`5xx`. Confirmar términos y límites vigentes antes de producción, especialmente uso no comercial y atribución. No prometer traducción de contenido externo.
- **Tres aplicaciones, cuarto repositorio documental y cambios de contrato:** mantener OpenAPI y fixtures sincronizados, bloquear merges incompatibles y usar una sola coordinación del plan; `GameBook.System` documenta los tres proyectos y no introduce un cuarto servicio ni un paquete de código compartido.
- **Traducción y publicación pública:** comprobar paridad EN/ES de cada Markdown de `GameBook.System`, verificar enlaces y excluir secretos, cachés y archivos locales antes de la única publicación inicial.
- **Prisma compartiendo base:** PostgreSQL ya impide al runtime acceder al esquema ajeno. Los migradores existentes tienen privilegios amplios, por lo que `GB-003.06` debe reemplazarlos para CI por roles SQL limitados y probar los permisos antes de guardar secretos. Incluso con roles limitados, revisar el SQL de cada migración y ejecutar secuencialmente antes del despliegue; no conceder `neon_superuser` a Actions como solución rápida.
- **Despliegue backend en Render:** comprobar el build, arranque, conectividad y logs reales de AuthUser/Game después de la aceptación local. No depender de procesos persistentes ni memoria local para sesión, revocación o consistencia; un fallo de despliegue se corrige antes de dar por cerrado `GB-012`.

Este plan define el trabajo, pero no acredita por sí mismo ninguna implementación o despliegue; los avances reales y sus evidencias se registran en `tasks/mvp.md`.
